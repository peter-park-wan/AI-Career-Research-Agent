# 第 1 课 · 后端地基：配置治理与错误体系

> 阶段 1 的第一课。目标不是"学会 FastAPI"，而是**建立服务层的两条地基线**：
> 配置的单一来源，和错误的分级出口。
> 这两样东西没立好，后面加异步任务、多副本、可观测全都会返工。

---

## 一、核心心智模型：Agent 项目里有「两条配置线」

这是本课最重要的一张表。改造前你的 `api.py` 把两者混在一起，这是后面所有麻烦的源头。

| | 进程级配置 `Settings` | Agent 运行时配置 `Configuration` |
|---|---|---|
| 文件 | `app/core/config.py`（本课新建） | `open_deep_research/configuration.py`（已有） |
| 内容 | 端口、CORS、Bearer Token、上传上限、DB/Redis 连接串、限流阈值、日志级别 | `research_model`、`search_api`、`max_reflection_rounds`、`rag_enabled`、`enable_github_search` |
| 谁改 | 运维 / 部署时定，进程启动读一次 | 每个请求可由前端 `configurable` 覆盖 |
| 变了会怎样 | 需要重启 | 下一个请求就生效 |
| 缺失时 | **必须启动失败**（fail fast） | 有合理默认值，正常跑 |
| 敏感度 | 高（含密钥、连接串） | 低（业务参数，可下发给前端做配置面板） |

**判断口诀**：
> 换个用户就变 → `Configuration`；换个部署就变 → `Settings`。

你项目里已有 `Configuration.from_runnable_config()` 会去读 `os.environ.get(field_name.upper())`（`configuration.py:516`），
意味着 `RESEARCH_MODEL=xxx` 既能当环境变量又能被 `configurable` 覆盖 —— 这本身没错，
但**它不该管端口和数据库连接串**。分层之后，`Settings` 不再出现在任何 `configurable` 里。

| 9 | SSE 手写、无 `event:` / `id:` 语义、`data: [DONE]` 是自定义约定 | `L555-591` | 协议设计（阶段 2 修） |

> 第 5 条最容易被忽略，也最能体现"全栈"功力：
> `async def write_profile()` 里执行一次 5MB 文件的同步 `open().write()`，
> 这一次调用会**卡住整个事件循环**——期间所有其他请求（包括 `/health`）全部排队。
> 正确做法是 `await anyio.to_thread.run_sync(...)` 把它丢到线程池。

## 四、本课已交付的示范代码

### 4.1 `app/core/config.py` — 六个值得学的细节

1. **`env_prefix="API_"`**：字段名即环境变量名（`bearer_token` ← `API_BEARER_TOKEN`），
   消灭了散落各处的 `os.getenv("API_XXX")` 字符串。
2. **`extra="ignore"`**：`.env` 里还有 `OPENAI_API_KEY` 等大量不属于本类的变量，
   忽略而不是报错，避免"加了个新 Key 就启动失败"。
3. **`NoDecode` + `field_validator`**：pydantic-settings 默认会用 JSON 解析复杂类型，
   `API_CORS_ORIGINS=*` 不是合法 JSON 会直接崩。显式关掉解码再自己 `split(",")`，
   把解析规则收口到一处（改造前 `L75` 是散着写的）。
4. **空白字符串 → `None`**：`.env.example:47` 写的是 `API_BEARER_TOKEN=`（有键无值）。
   不处理就会得到 `""` 而非 `None`，导致 `is None` 判断静默失效 —— 隐形 bug。
5. **`MEMORY_STORE` 走 `validation_alias`**：这个变量在 `.env` 里没有 `API_` 前缀，
   别名一旦声明，`env_prefix` 对该字段失效。演示了"前缀是约定，别名的例外情况"。
6. **`assert_production_ready()`**：这是全课的灵魂。
   `ENV=prod` 时强校验 CORS 不含 `*`、必须有 Bearer Token、checkpointer 不能是内存版。
   每一条都对应一个真实事故：CORS `*` + `allow_credentials=True` 可被任意站点带 Cookie 调接口；
   无 Token 则含手机号的简历可被任意人拉取；内存 checkpointer 在多副本下会话随机错乱。

### 4.2 `app/core/errors.py` — 四个值得学的细节

1. **`status_code` / `code` 定义在类上**：调用方写 `raise NotFoundError("档案", name)`，
   不用重复写 `404`，也不可能写错。
2. **`operational` 标志区分"业务错误"与"程序缺陷"**：
   前者记 `warning` 不告警，后者记 `error` + 堆栈并告警。
   这解决了"用户传错参数也触发 P0 告警"的经典噪音问题。
3. **`UpstreamError` 独立成类 + `is_retryable()`**：
   把"LLM 抽风"和"参数不合法"分开，重试策略才能做出正确判断（阶段 2 直接复用）。
4. **全局处理器收敛所有出口**：
   - `AppError` → 业务错误统一响应体
   - `RequestValidationError` → 整形为字段级 `fields` 数组，前端可直接贴到输入框旁
   - `StarletteHTTPException` → 兜住框架自身的 404 等
   - `Exception` → 最后防线，**只返回安全话术，绝不把 `str(exc)` 发给客户端**
   全部响应体统一为 `{title, status, detail, request_id}`。

## 五、练习（按顺序做，做完再进下一课）

### 练习 1.1 · 验证 fail fast（10 分钟）
在 `app/core/config.py` 同级新建一个临时脚本，验证三种场景；然后在项目根目录跑：

```powershell
# 场景 A：默认 dev，应正常输出配置
python -c "from app.core.config import get_settings; print(get_settings().port)"

# 场景 B：prod + CORS=*，应抛 ConfigError 并写清原因
# 注意：字段 env 在 env_prefix="API_" 下对应 API_ENV（不是 ENV）
$env:API_ENV='prod'; $env:API_CORS_ORIGINS='*'
python -c "from app.core.config import get_settings; get_settings()"
Write-Host "exit=$LASTEXITCODE"      # 期望 exit=1
Remove-Item Env:API_ENV; Remove-Item Env:API_CORS_ORIGINS

# 场景 C：逗号分隔的 CORS 能被正确切成列表
$env:API_CORS_ORIGINS='http://a.com, http://b.com'
python -c "from app.core.config import get_settings; print(get_settings().cors_origins)"
Remove-Item Env:API_CORS_ORIGINS
```

**实测输出（已跑通）**
```
场景 A → 8000
场景 B → app.core.errors.ConfigError: 生产环境配置校验未通过：
           - 生产环境禁止 API_CORS_ORIGINS=*，请填写明确的来源列表
           - 生产环境必须设置 API_BEARER_TOKEN
           - 生产环境 API_CHECKPOINTER 不能是 memory（多副本下会话会错乱），请设为 postgres 或 redis
         exit=1
场景 C → ['http://a.com', 'http://b.com']
```

**验收**：场景 B 打印出中文的、可读的失败原因，且进程非 0 退出。
**顺带学到一个坑**：`env_prefix` 是"一刀切"的，`env` 字段拿到的是 `API_ENV`。
如果想让环境变量叫得更清楚，可以把字段改名为 `app_env`（→ `API_APP_ENV`），或者用 `validation_alias="ENV"`。
